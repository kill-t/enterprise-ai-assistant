# Vue 知识库编辑、软归档与恢复

## 1. 本模块解决什么问题

上一模块只能查看和创建知识库。用户创建后如果名称写错，或者项目结束需要暂停检索，还必须直接调用
后端接口。本模块补齐知识库生命周期管理：

```text
编辑名称或描述 → PATCH
归档活动知识库 → DELETE（软归档）
恢复归档知识库 → PATCH is_archived=false
```

页面现在可以完整管理知识库元数据和使用状态，但仍不会物理删除知识库、文档或引用快照。

## 2. 知识库状态机

第一版只有两个业务状态：

```text
ACTIVE（使用中）
  │
  │ DELETE /knowledge-bases/{id}
  ▼
ARCHIVED（已归档）
  │
  │ PATCH {"is_archived": false}
  ▼
ACTIVE（使用中）
```

归档后：

- 默认知识库列表不再返回它。
- 它停止参与 RAG 检索。
- 文档、Chunk 和历史引用不会被物理删除。
- 用户可以从“显示已归档”列表恢复。

因此页面使用“归档”和“恢复使用”，不使用“永久删除”和“重新创建”。

## 3. 为什么编辑必须使用本地副本

点击编辑时，组件复制当前值：

```text
editName = knowledgeBase.name
editDescription = knowledgeBase.description ?? ""
```

输入框绑定的是副本，不是列表中的原对象。这样用户输入或取消时：

- 卡片不会提前变化。
- 后端失败不需要执行回滚。
- Store 仍代表最后一次由服务器确认的数据。

真实流程是：

```text
复制当前值
→ 用户修改副本
→ 前端校验
→ Store.updateKnowledgeBase
→ API PATCH
→ 后端成功返回完整对象
→ Store 替换对应列表项
→ 关闭对话框
```

## 4. 为什么不是乐观更新

乐观更新会先改变卡片，再请求后端。如果名称重复返回 409，页面必须保存旧快照并回滚。知识库编辑不是
高频即时交互，等待一次后端响应的体验成本很低，因此第一版采用“后端确认后更新”。

这也让失败行为更容易理解：

```text
PATCH 失败
→ 原卡片保持不变
→ 编辑对话框保持打开
→ 在表单附近显示后端错误
```

## 5. 前端校验和后端校验怎样配合

编辑表单执行：

- 名称去掉两端空格后不能为空。
- 名称最多 255 个字符。
- 描述最多 4000 个字符。
- 纯空格描述转换为 `null`，表示清空描述。

这些校验提供即时反馈。后端仍会使用 Pydantic 和数据库唯一约束再次保护请求，因为攻击者或其他客户端
可以绕过 Vue 页面。

名称重复就是典型的后端业务错误：前端无法仅凭当前列表判断数据库中是否冲突，必须以 409 响应为准。

## 6. 为什么归档仍需要确认

归档可以恢复，但会立即改变系统行为：

- 不再参与问答检索。
- 默认列表中消失。
- 已绑定会话后续不会再从它获取证据。

因此点击卡片上的“归档”只打开确认框，不发送请求。用户再次点击“确认归档”后才调用 Store。

确认框明确说明：

```text
停止参与检索
不会物理删除文档
以后可以恢复
```

这比只写“确定吗”更能帮助用户理解实际业务后果。

## 7. 为什么归档失败时不能自动关闭确认框

归档可能因为正在运行的入库任务、网络故障或权限状态变化而失败。流程是：

```text
确认归档
→ 按钮显示“正在归档…”并禁用
→ 后端失败
→ 原卡片保留
→ 确认框保持打开
→ 显示 actionErrorMessages[id]
```

如果失败后直接关闭，用户可能误以为操作成功，还需要重新寻找目标才能看到错误。

## 8. 恢复为什么不需要二次确认

恢复只会重新启用知识库参与检索，不会删除数据或降低可用性。因此点击“恢复使用”可以直接发送：

```json
{"is_archived": false}
```

后端返回完整知识库对象后，Store 将卡片的“已归档”替换成“使用中”。如果失败，错误显示在对应卡片
下方，不影响其他知识库。

## 9. 同一知识库怎样防止并发操作

编辑、归档和恢复复用 Store 的对象级锁：

```text
isUpdatingKnowledgeBase(id)
isArchivingKnowledgeBase(id)
isManagingKnowledgeBase(id)
```

只要同一 ID 有请求未结束，该卡片的其他管理按钮都会禁用。不同知识库仍可独立操作。

这样可以避免：

```text
编辑 PATCH 尚未返回
→ 用户又点击归档
→ 两个响应顺序不确定
→ 较晚响应覆盖较新的业务状态
```

## 10. 错误为什么按知识库 ID 保存

Store 使用：

```text
actionErrorMessages[knowledgeBaseId]
```

页面根据当前交互决定显示位置：

- 编辑失败：编辑对话框内。
- 归档失败：归档确认框内。
- 恢复失败：对应知识库卡片下方。

打开一个新的编辑或归档操作前调用 `clearActionErrorMessage(id)`，防止上一次失败提示错误地出现在新
操作中。

## 11. 为什么请求期间禁止关闭对话框

普通 HTTP PATCH 或 DELETE 发出后，关闭对话框并不能真正取消服务器操作。如果按钮仍在请求中却允许
用户关闭，用户可能认为请求已经撤销。

当前规则是：

```text
isEditing / isArchiving 为 true
→ 禁用输入和按钮
→ 点击遮罩或取消不会关闭
→ 等待成功或失败终态
```

以后如果确实需要取消，应增加 AbortController，并确认后端是否支持幂等取消，而不是只隐藏 UI。

## 13. 测试保护了什么

新增页面测试覆盖：

- 编辑框复制当前名称和描述。
- 编辑提交前去空格，空描述转换为 `null`。
- 后端成功后替换卡片并关闭对话框。
- 名称为空时不发送 PATCH。
- 后端拒绝编辑时保留原卡片和对话框错误。
- 点击归档只打开确认框，不立即请求。
- 归档期间按钮禁用并显示处理中状态。
- 归档成功后从活动列表移除。
- 归档失败保留原卡片、确认框和中文错误。
- 已归档知识库通过 PATCH 恢复为使用中。

## 14. 本模块尚未做什么

- 没有文档上传和文档列表。
- 没有显示文档解析、分块和 Embedding 状态。
- 没有失败入库任务重试按钮。
- 没有知识库详情路由。
- 会话页面还不能选择知识库。

下一小步是 **RAG-6D：Vue 文档 API 与状态层**。先建立文档响应契约、multipart 上传请求、文档列表、
状态查询、重试和软删除的 API Client 与 Store，然后再单独制作上传界面和状态轮询。

## 15. 常见错误

| 现象 | 原因与处理 |
| --- | --- |
| 输入名称时卡片也跟着变化 | 编辑框直接绑定了列表对象，没有创建副本 |
| PATCH 失败后需要复杂回滚 | 使用了不必要的乐观更新 |
| 点击归档立即消失 | 缺少对检索影响的二次确认 |
| 归档文案写“永久删除” | 混淆了软归档和物理删除 |
| 请求中关闭对话框后仍被归档 | 隐藏 UI 不等于取消 HTTP 请求 |
| 一个知识库操作时全列表禁用 | 使用全局锁，没有按 ID 管理状态 |
| 编辑失败错误跑到别的卡片 | 错误没有按知识库 ID 保存 |
| 恢复调用 POST 或重新创建 | 恢复应是同一资源的 PATCH 状态转换 |

## 16. 面试表达

> 我把知识库设计为 ACTIVE 和 ARCHIVED 两态。DELETE 在后端是软归档，页面会说明它停止参与检索但
> 不删除文档，并要求二次确认；恢复通过 PATCH is_archived=false。编辑表单使用本地副本，不直接修改
> Pinia 列表，后端成功后才替换卡片，所以 409 重名失败不需要回滚。更新、归档和恢复复用 ID 级互斥
> 状态，不同知识库仍能并行操作，错误也按 ID 显示在当前对话框或卡片附近。

## 17. 小练习（约 15–20 分钟）

为恢复失败增加页面测试：

1. 列表返回一条已归档知识库。
2. `updateKnowledgeBase` 抛出 `ApiError("暂时无法恢复", ...)`。
3. 点击“恢复使用”。
4. 断言 PATCH 参数是 `{ is_archived: false }`。
5. 断言卡片仍显示“已归档”。
6. 断言卡片附近显示“暂时无法恢复”。

运行：

```powershell
npm run test:run -- KnowledgeBasesView.test.ts
```

答案要点：失败响应不能改变原对象，错误来自 `actionErrorMessages[knowledgeBase.id]`。
