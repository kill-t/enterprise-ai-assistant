# 中文代码注释与阅读约定

## 为什么要统一注释

这个项目既是可运行的作品，也是用于学习和面试讲解的代码库。统一的中文注释可以帮助
阅读者先理解每层的职责和业务意图，再进入具体实现。

## 两类注释

### 文档字符串

每个类、函数和异步函数都使用中文文档字符串，说明它负责什么或保证什么。例如 Service
方法描述业务动作，Repository 方法描述数据库读写边界，测试函数描述它保护的行为。

### 行内注释

行内注释只放在无法从代码本身直接看懂的决策前，例如：

- 为什么先保存用户消息，再调用模型。
- 为什么先创建 `pending` 助手消息。
- 为什么 Redis 失败后回退到 PostgreSQL。
- 为什么历史消息需要逆序裁剪。

不为赋值、返回值等显而易见的语句逐行添加注释。这样的注释会制造噪声，并且容易在代码
变化后失真。

## 阅读真实调用链

当前发送消息的主链路是：

```text
FastAPI Router
→ ConversationService
→ ConversationRepository / MessageRepository
→ PostgreSQL
→ LLM Provider
→ Redis Memory（可降级缓存）
```

建议先阅读每个类和函数的文档字符串，再跟随 `ConversationService.send_message()` 中的行内
注释观察状态变化。数据库保存业务事实，Redis 只加速历史上下文读取，因此 Redis 异常不会
回滚已经成功提交的消息。

## 维护规则

- 新增类或函数时同步编写中文文档字符串。
- 复杂分支说明“为什么这样处理”，不要只复述“代码做了什么”。
- 代码标识符、API 字段、错误码和协议名称保持英文，避免破坏生态约定。
- 修改逻辑时同步检查相邻注释，避免注释与行为不一致。
- 测试的文档字符串应描述受保护的行为，而不是重复测试函数名。

## 小练习

阅读 `ConversationService.send_message()`，用自己的话解释：

1. 为什么用户消息和助手消息分别提交。
2. 为什么失败的助手消息不能写入 Redis 上下文。
3. 哪一段代码保证 Redis 故障不会让对话主流程失败。

答案要点：用户消息是已经发生的业务事实；助手消息有独立的 `pending → completed/failed`
生命周期；只有完成消息才能参与后续模型上下文；缓存异常在 `_get_history()` 和
`_save_to_memory()` 的边界内被捕获并降级。
