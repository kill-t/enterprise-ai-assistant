# 模块 04：消息状态与模型失败处理

## 要解决的问题

调用模型是外部操作，可能超时、网络异常或被服务端拒绝。若只在接口中返回异常，
数据库无法说明用户问题处理到了哪一步；前端也无法区分“没有回复”和“回复生成失败”。

## 状态流转

```text
用户消息：completed
    ↓
助手消息：pending
    ↓
调用模型
    ├─ 成功 → completed
    └─ 失败 → failed
```

`pending` 表示助手消息记录已创建，但模型调用尚未完成；`failed` 表示调用已结束且失败，
不是消息丢失。

## 数据设计

`messages` 新增：

- `error_code`：机器可识别的稳定错误码，例如 `MODEL_TIMEOUT`。
- `error_message`：可以安全展示给用户的中文提示，不保存底层 Provider 的原始异常。
- `finished_at`：模型调用成功或失败的结束时间。

对应 Alembic 迁移会升级已有数据库。消息接口响应也新增状态、错误码、错误提示和完成时间。

## 调用流程

```text
1. 保存用户消息并提交
2. 创建 pending 助手消息并提交
3. 调用模型
4. 成功：更新助手内容、token、状态和完成时间并提交
5. 失败：更新失败状态、错误信息和完成时间并提交
6. 失败时返回 502 或 504；前端可重新拉取消息列表查看失败记录
```

数据库提交后才会写 Redis。只有 `completed` 消息会进入 Redis 和后续上下文；
`pending` 与 `failed` 消息不会污染记忆和摘要。

## 为什么不回滚用户消息

用户消息已被服务器接收并持久化，这是事实。模型失败不代表用户没有提问，而是系统未能
完成回复。保留用户消息和失败助手消息，才能支持审计、重试和前端正确展示。

## 测试说明

测试使用会抛出超时异常的 Fake Provider，验证：

- 返回 `MODEL_TIMEOUT` 和 HTTP 504。
- 用户消息为 `completed`。
- 助手消息先被创建，最终更新为 `failed`。
- 失败信息和完成时间被保存。
- Redis 只接收到用户消息，没有接收到失败助手消息。

## 面试表达

“模型调用被视为不可靠的外部依赖。我先持久化 pending 状态的助手消息，再根据调用结果
更新为 completed 或 failed。失败记录保留安全错误码和时间，但不泄露 Provider 原始异常；
同时失败消息不进入对话记忆，避免影响后续上下文。”

## 小练习

如果用户点击“重试”，你会复用失败助手消息，还是创建一条新的助手消息？请思考如何避免
用户连续点击重试导致同一个问题被模型调用多次。
