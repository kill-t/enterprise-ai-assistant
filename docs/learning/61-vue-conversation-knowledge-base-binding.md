# Vue 会话知识库选择与原子绑定

## 1. 本模块解决什么问题

之前已经完成：

- 创建知识库。
- 上传和入库文档。
- 后端按会话绑定知识库。
- 聊天根据绑定检索并返回引用。
- 前端展示回答引用。

但用户在页面上还无法决定“哪个会话使用哪些知识库”。知识库管理和 RAG 聊天虽然各自可用，用户流程并未真正连接。

本模块补齐：

```text
进入会话
→ 查看当前绑定
→ 选择一个或多个活动知识库
→ 保存完整选择
→ 后续消息使用新的检索范围
```

没有绑定时，后续消息仍是正常聊天，不会执行企业知识检索。

## 2. 整体调用链

```text
ConversationDetailView
→ ConversationKnowledgeBaseSelector
→ ConversationKnowledgeBaseBindingStore
→ Conversation Knowledge Base API Client
→ FastAPI Conversation Router
→ ConversationKnowledgeBaseService
→ PostgreSQL conversation_knowledge_bases
```

各层职责：

- 会话详情页：决定当前会话 ID，生成期间禁用配置。
- 选择器组件：展示摘要、复选框、保存和错误。
- 绑定 Store：区分服务端快照与未保存草稿，处理并发响应。
- API Client：负责 GET、PUT、Token 和 URL 编码。
- 后端 Service：验证会话、知识库所有权与归档状态，控制事务。
- PostgreSQL：保存真实绑定关系。

## 3. 为什么使用独立 Store

现有 `ConversationDetailStore` 已经负责：

- 会话元数据。
- 历史消息。
- SSE 流式生成。
- 取消生成。
- 失败消息重试。

绑定编辑包含另一组状态：

- 服务端已保存知识库。
- 本地复选框草稿。
- 加载和保存状态。
- 选择上限错误。
- 归档旧绑定。
- 保存失败恢复。

如果全部塞进消息 Store，它会同时管理“聊天运行时”和“知识范围配置”，职责过大。

独立 Store 使调用链更清楚：

```text
消息变化 → ConversationDetailStore
知识范围变化 → ConversationKnowledgeBaseStore
```

退出登录时，两个 Store 都由 `resetUserDataStores` 统一清理。

## 4. 后端接口契约

### 4.1 读取绑定

```http
GET /api/v1/conversations/{conversation_id}/knowledge-bases
```

响应：

```json
{
  "conversation_id": "...",
  "knowledge_bases": []
}
```

响应返回完整知识库公开字段，而不只是 ID，因此页面不需要额外逐个请求名称和归档状态。

### 4.2 原子替换绑定

```http
PUT /api/v1/conversations/{conversation_id}/knowledge-bases
```

请求：

```json
{
  "knowledge_base_ids": ["id-1", "id-2"]
}
```

空数组表示解除全部绑定：

```json
{
  "knowledge_base_ids": []
}
```

## 5. 为什么是 PUT 整组替换

替代方案是为每个复选框发送独立接口：

```text
POST   /bindings/{knowledge_base_id}
DELETE /bindings/{knowledge_base_id}
```

如果用户一次修改三个选项，就会产生多个请求：

```text
删除 A 成功
增加 B 成功
增加 C 失败
```

此时页面与数据库可能停在半套结果。

当前 PUT 把完整目标集合一次交给后端：

```text
校验全部 ID
→ 删除旧绑定
→ 插入新绑定
→ 同一数据库事务提交
```

只会出现两种结果：

- 全部成功。
- 全部失败并回滚。

这就是原子替换。

## 6. 服务端快照与本地草稿

Store 同时保存：

```ts
boundKnowledgeBases
selectedKnowledgeBaseIds
```

含义不同：

- `boundKnowledgeBases`：最近一次由后端确认的事实。
- `selectedKnowledgeBaseIds`：用户正在编辑、尚未保存的草稿。

打开编辑器时：

```text
服务端快照 → 复制成草稿
```

勾选复选框只修改草稿。摘要区域仍显示服务端快照，不能让用户误以为未保存选择已经生效。

保存成功后：

```text
后端响应 → 同时替换快照和草稿
```

保存失败后：

```text
快照保持不变
草稿保持用户刚才的选择
编辑器保持打开
显示后端错误
```

用户可以直接重试，不需要重新勾选。

取消编辑时，不重新请求后端，只把草稿恢复成最近一次服务端快照。

## 7. 为什么显式点击保存

另一种方案是勾选立即保存。

它的问题：

- 连续勾选会产生多个 PUT。
- 后返回的旧请求可能覆盖新选择。
- 用户难以判断哪些选择已经保存。
- 一次失败会留下难以解释的中间状态。

显式保存把多次本地修改合并为一个原子请求，也更适合展示“草稿”和“事实”的区别。

## 8. 最多选择五个

后端 Pydantic 契约限制：

```text
knowledge_base_ids 最多 5 个
```

前端 Store 使用相同限制提供即时提示：

```text
每个会话最多选择 5 个知识库
```

限制原因：

- 控制一次检索的候选规模。
- 控制 Prompt 证据量。
- 控制向量检索延迟。
- 避免用户把所有资料库无差别加入每个会话。

前端限制是体验优化，后端限制才是最终业务约束。

## 9. 已归档旧绑定如何处理

可能发生：

```text
会话绑定知识库 A
→ 后来用户归档 A
→ 再次打开旧会话
```

后端 GET 仍返回这个既有绑定，方便审计；实际检索会跳过归档知识库。

页面必须：

- 继续显示 A。
- 标记“已归档，不参与检索”。
- 允许用户取消选择。
- 不允许重新选择一个已经取消的归档项。
- 仍选中归档项时阻止 PUT，并提示先取消。

不能悄悄隐藏归档绑定，否则用户不知道为何会话绑定数量和实际检索范围不一致，也无法明确清理旧关系。

## 10. 活动列表与归档绑定如何合并

选择器需要两个来源：

```text
KnowledgeBaseStore → 当前用户活动知识库
BindingStore       → 当前会话既有绑定，可能含归档项
```

组件按 ID 合并：

1. 先加入活动知识库。
2. 再补充列表中不存在的既有绑定。
3. 同一个 ID 只出现一次。

因此新选择只来自活动知识库，旧归档绑定仍然可见。

## 11. 快速切换会话的竞态

假设用户快速从 A 切到 B：

```text
GET A 发出
→ 切换到 B
→ GET B 发出
→ GET B 先返回
→ GET A 后返回
```

如果没有保护，A 的迟到响应会覆盖 B 的选择器。

Store 使用递增版本号：

```text
loadRequestVersion
saveRequestVersion
```

每个请求记录自己发出时的版本。响应写入前同时检查：

- 版本仍是最新。
- 当前 conversationId 仍与请求一致。

任意条件不满足，就丢弃迟到结果。

保存也使用独立版本，防止会话 A 尚未结束的 PUT 覆盖会话 B。

## 12. 为什么生成期间禁止修改绑定

一次 RAG 生成在开始时读取会话绑定，并根据当时的范围检索证据。

如果生成过程中页面允许修改，用户可能看到新选择并误以为当前回答也使用了它。

因此会话详情把下面状态传给选择器：

```text
detailStore.isSending
```

生成期间配置按钮禁用，并提示：

```text
AI 生成结束后可修改知识库绑定
```

这主要是交互一致性。后端仍要保证一次请求内部使用稳定状态。

归档会话也禁用修改，因为它不再用于继续对话。

## 13. 无绑定为什么不是错误

企业助手不应该强迫所有消息都走 RAG。

无绑定时：

```text
未绑定知识库
→ 普通聊天
→ 不执行向量检索
→ 不返回知识库引用
```

页面明确展示：

```text
未绑定知识库，后续消息将使用普通聊天
```

如果用户还没有知识库，会提供“前往创建知识库”入口。

## 14. 页面位置与交互

选择器放在：

```text
会话标题
→ 会话知识库摘要 / 配置
→ 消息历史
→ 消息输入框
```

用户在提问前能看到当前检索范围，也不会让配置控件混入消息列表。

摘要态只展示后端确认的绑定；编辑态显示：

- 可选择知识库卡片。
- 当前选择数量。
- 五个上限。
- 归档警告。
- 取消和保存按钮。
- 保存错误。

## 17. 常见错误

### 错误一：摘要直接显示草稿

用户会误以为未保存选择已经生效。

### 错误二：每勾选一次就请求后端

产生无意义请求，并增加乱序与部分成功风险。

### 错误三：只保存知识库 ID，不保留服务端对象

归档状态和名称还要额外查询，容易与实际绑定快照不一致。

### 错误四：隐藏归档旧绑定

用户无法理解实际状态，也不能明确解除它。

### 错误五：没有处理会话切换竞态

迟到的 A 响应可能覆盖当前 B 会话。

### 错误六：无绑定显示为异常

普通聊天是正常降级路径，不是错误。

## 18. 面试表达

> 我把会话的 RAG 范围设计为显式知识库绑定。前端区分后端确认的绑定快照和未保存多选草稿，用户完成选择后用一次 PUT 原子替换完整集合，避免逐项请求导致部分成功。Store 对加载和保存分别使用版本号，防止快速切换会话时迟到响应污染当前状态。既有绑定后来归档时不会从 UI 消失，而是标记为不参与检索并允许用户取消。生成期间配置入口禁用，避免用户误判当前回答使用了刚修改的范围。

## 19. 小练习

练习时间约 15～30 分钟。

请回答：

1. 为什么摘要区域应该显示 `boundKnowledgeBases`，而不是 `selectedKnowledgeBaseIds`？
2. 用户把选择顺序从 `[A, B]` 改成 `[B, A]`，为什么不应该视为内容变化？
3. GET A 比 GET B 晚返回时，Store 通过哪两个条件阻止 A 覆盖 B？

可选代码练习：增加一个测试，模拟会话 A 的保存请求未完成就切到会话 B，确认 A 的保存响应不会覆盖 B。

答案要点：

- 摘要表示服务端事实，selected 是未保存草稿。
- 当前绑定表达集合，不依赖勾选顺序。
- 同时检查请求版本和当前 conversationId。
