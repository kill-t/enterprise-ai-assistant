# 66. RAG 困难评测集与指标诊断

## 这一模块解决什么问题

上一版只有一份短文档和 14 道题，很多问题直接复述资料原词。这样的测试可以证明检索链路能运行，却不能证明系统能够处理真实企业知识库。

真实知识库通常同时存在：

- 用户用另一种说法提问。
- 一个答案分散在多份文件里。
- 历史资料与现行资料使用相似术语。
- 文档只提到某个主题，却没有用户追问的具体事实。

因此本模块增加 4 份语料和 35 道困难问题，并让评测报告能够按场景标签诊断。

## 在整体架构中的位置

```text
版本化受控语料
  ↓ 正式上传 API
MinIO 原文件 + PostgreSQL 持久化任务
  ↓ Celery Worker
解析 → 分块 → Embedding → pgvector
  ↓ KnowledgeSearchService
逐题检索观测
  ↓ RagMetricsEvaluator
整体指标 + 标签指标 + 脱敏基线
```

评测不是另一套 RAG。它调用正式的 `KnowledgeSearchService`，因此会经过真实所有权过滤、Embedding Provider、pgvector 查询和相似度阈值。

## 为什么加入历史干扰文档

`white-dolphin-legacy-notes.md` 描述一个旧项目。它故意与蓝鲸共享“会议时间”“存储”“消息队列”“权限”等术语，但负责人、年份和技术方案不同。

这模拟企业最常见的数据问题：错误资料不是完全无关，而是很像正确资料。如果只用随机百科问题测试拒答，阈值很容易得到虚假的高分。

## 35 道题如何组成

- 25 道可回答题。
- 10 道必须拒答的题。
- 14 道同义改写题。
- 5 道带“多文档”标签的题。
- 7 道带“近似干扰”标签的题。
- 10 道困难拒答题。

一个问题可以同时属于多个标签。例如对比蓝鲸和白海豚负责人与存储方案的问题，同时属于“多文档”和“近似干扰”。

## 标准证据是什么

每道可回答题都声明：

```json
{
  "filename": "blue-whale-project-charter.md",
  "content_contains": "项目负责人是林晓"
}
```

评测只有在下面两个条件同时满足时才算命中：

1. 检索结果文件名与标准文件一致。
2. 返回的完整 Chunk 包含指定原文片段。

只返回同一主题的其他段落不算命中。测试还会逐条确认标准片段确实存在于版本化语料，防止改了文档却忘记更新答案标签。

## 两个容易混淆的准确率

旧字段 `refusal_accuracy` 实际统计了所有题：

```text
答案题有检索结果 → 正确
拒答题没有检索结果 → 正确
```

这其实是“整体行为准确率”，并不等于“拒答题准确率”。本轮拆成：

```text
behavior_accuracy
= 所有回答/拒答决策正确数 ÷ 全部问题数

refusal_accuracy
= 正确拒答数 ÷ 标准拒答题数
```

例如答案题全部正常，但 10 道拒答题只拒答 1 道：整体行为准确率仍可能看起来不低，而拒答题准确率只有 10%。两个指标一起看，才能发现系统是否在资料不足时乱给证据。

旧 JSON 基线仍能读取：模型使用兼容别名把旧的 `refusal_correct` 转换为新的 `behavior_correct`，避免历史评测资产突然失效。

## 按标签诊断

总体平均值只能说明“有问题”，不能说明问题在哪里。`tag_metrics` 对每个标签分别计算：

- 样例数、答案题数和拒答题数。
- Recall@K 与 MRR。
- 整体行为准确率。
- 该标签存在拒答题时的拒答题准确率。

标签样例数较少时不能把百分比当作稳定统计结论，但它适合定位下一步实验方向。

## 本次真实结果

| 模式 | Recall@3 | MRR | 整体行为准确率 | 拒答题准确率 |
| --- | ---: | ---: | ---: | ---: |
| Mock Hash | 57.00% | 55.33% | 65.71% | 40.00% |
| text-embedding-v4 | 76.67% | 79.33% | 74.29% | 10.00% |

真实模型的同义改写 Recall@3 为 78.57%，明显高于 Mock 的 50.00%，说明语义 Embedding 有价值。

真实模型的困难拒答只有 10.00%。这并不是模型“差”，而是当前规则只在问“问题与 Chunk 是否相似”，业务真正需要问的是“Chunk 是否包含足以回答问题的事实”。

资料写着“后续会加入 OCR”，与“OCR 哪天上线”高度相关，但它没有日期。向量相似度无法独立完成答案充分性判断。

## 为什么不继续只调阈值

提高阈值可以减少误召回，但也会删除正确证据：

```text
阈值降低 → Recall 通常升高，误答风险也升高
阈值提高 → 拒答通常增多，正确答案也可能被误拒
```

困难拒答中的错误 Top 分数与部分正确答案分数重叠，因此不存在一个明显的全局分界线。阈值仍然有用，但它只能作为粗过滤，不应该承担全部答案充分性判断。

## 下一阶段为什么选择两阶段检索

计划的数据流是：

```text
问题
→ 第一阶段扩大候选召回
→ 第二阶段重排序并判断候选是否回答问题
→ 只把充分证据交给回答层
→ 没有充分证据则拒答
```

第一阶段优先保证不要漏掉证据；第二阶段负责区分“同主题”和“真答案”。后续会比较：

- pgvector 语义召回。
- PostgreSQL 全文关键词召回。
- 两路结果的 RRF 融合。
- 可替换的 Reranker / Answerability Judge。

MQE 和 HyDE 暂缓。它们主要扩大或改写查询，当前首要问题却是召回内容过于相关但不足以回答，过早增加查询反而可能带来更多相似干扰。

## 测试分别保护什么

- 数据集测试：数量、答案/拒答比例、标签覆盖和问题唯一性。
- 语料一致性测试：每条标准证据都真实存在于指定文件。
- 拒答标注测试：未知关键事实不能原样藏在语料中。
- 指标单元测试：答案题误拒答不会污染“拒答题准确率”。
- 兼容测试：旧基线仍能通过新模型读取。
- 回归测试：现有上传、Worker、检索、聊天和引用功能不受影响。

## 本轮遇到的两个典型错误

### Windows 事件循环错误

临时脚本直接使用 `asyncio.run` 时，Windows 选择了 psycopg 不支持的 ProactorEventLoop。项目已有 `run_async` 封装，会选择 SelectorEventLoop。复用封装后恢复正常。

这说明基础设施兼容逻辑应集中管理，不应在每个脚本里复制。

### 停用用户返回 403

脚本最初选择数据库里最早的用户，但该用户已经停用。Token 虽能签发，认证依赖仍正确返回 403。脚本改为只选择 `is_active = true` 的用户。

排查时应区分：401 表示 Token 无效、过期或签名错误；403 表示身份存在，但账号状态或策略不允许操作；404 表示当前用户看不到目标资源，可能不存在或不属于他。

## 面试时如何表达

可以这样说明：

> 我没有把单份文档的高分当作 RAG 完成，而是构造了带历史干扰资料的 35 题评测集。真实 Embedding 将 Recall@3 从 57% 提升到 76.67%，但困难拒答仅 10%。这证明向量相似度能解决语义召回，却不能判断证据是否充分。因此我保留语义检索，同时把下一阶段设计为候选召回加答案充分性判断，并用相同数据集验证改进，而不是凭感觉加入 MQE 或 HyDE。
