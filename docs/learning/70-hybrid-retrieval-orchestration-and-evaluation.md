# 70. 混合检索编排、渠道降级与真实评测

## 这一模块解决什么问题

前两个模块已经分别具备：

- 真实向量检索：理解同义表达和语义相近内容。
- 真实 `pg_trgm`：补充技术术语、项目代号、日期和原词命中。
- RRF：按两路名次计算融合排名。

但“有两个 Retriever”不等于系统已经完成混合检索。本模块增加 `HybridRetriever`，统一负责调用渠道、校验来源、处理故障并生成融合候选。

## 在整体架构中的位置

```text
用户问题与知识库范围
  ↓
HybridRetriever
  ├─ KnowledgeSearchVectorRetriever
  │    └─ 现有 KnowledgeSearchService → Embedding → pgvector
  └─ PgTrgmLexicalRetriever → PostgreSQL pg_trgm
  ↓
ReciprocalRankFusion
  ↓
HybridRetrievalCandidate
  ↓
未来的 EvidenceSelector
```

当前线上搜索和聊天没有切换到 Hybrid。原因不是代码未完成，而是真实评测没有证明等权 RRF 优于现有真实向量方案。

## 为什么先输出候选，不直接接聊天

当前默认 `ThresholdEvidenceSelector` 使用向量相似度阈值，例如 `0.45`。RRF 分数的计算方式却是：

```text
1 / (rank_constant + rank)
```

当 `rank_constant=60` 时，两路共同命中的第一名大约只有：

```text
1/61 + 1/61 ≈ 0.0328
```

如果直接把它送入 `0.45` 的向量阈值，所有候选都会被错误删除。如果把阈值改成 0，又会把“相关但不能回答”的候选全部放行。

因此两类分数必须明确分开：

- `vector_score`：向量渠道内的原始余弦相似度。
- `lexical_score`：词法渠道内的原始 trigram 相似度。
- `fused_score`：只表达 RRF 融合名次，不能当作答案可靠度。

## HybridRetrievalRequest 的两个预算

请求同时保存：

- `channel_candidate_limit`：每个渠道最多召回多少条。
- `result_limit`：RRF 最终最多保留多少条。

本轮真实评测采用：

```text
向量候选 12 条
词法候选 12 条
RRF 最终候选 3 条
```

扩大第一阶段候选是为了让另一渠道有机会补充或纠正排名；最终仍只评测 Top-3，保持和旧基线的指标口径一致。

两个预算不能合成一个。假设每路只取 3 条再融合，正确 Chunk 若在某一路排第 4，就永远没有进入融合的机会。

## 真实向量 Adapter 为什么复用旧 Service

`KnowledgeSearchVectorRetriever` 没有重新实现：

- 用户所有权校验。
- 知识库归档判断。
- Embedding 配置兼容性。
- 查询向量生成。
- pgvector SQL。

它先批量读取当前用户的知识库，再调用现有 `KnowledgeSearchService.search_many()`。工厂函数把旧阈值临时设为 `-1`、候选倍率设为 `1`：

```text
候选不在进入 RRF 前被旧向量阈值删除
传入 Top-K 就等于当前渠道预算
```

Adapter 最后把现有响应映射成 `VectorRetrievalCandidate`。这种设计让旧功能继续由原有测试保护，混合层只增加适配，不复制业务规则和 SQL。

## 为什么恢复知识库请求顺序

SQL 的 `WHERE id IN (...)` 不保证返回顺序。Adapter 会：

```text
批量查询当前用户拥有的知识库
→ 核对没有缺失 ID
→ 按请求中的 ID 顺序重新排列
→ 交给现有多知识库检索
```

如果少返回一个 ID，可能代表资源不存在或属于其他用户，此时抛出 `VectorRetrievalScopeError`，不会继续生成 Embedding。

## 为什么权限错误不能降级

需要区分三类状态：

```text
渠道成功但候选为空
→ 正常“没有候选”

Embedding 超时或 pg_trgm 故障
→ 可用性问题
→ 使用另一条成功渠道降级

知识库不存在、越权或已归档
→ 请求范围无效
→ 立即停止，不能降级掩盖
```

如果越权后降级为空结果，上层可能把它解释成“资料里没有答案”，既改变既有 404 语义，也让安全问题更难排查。

## 单路和双路失败如何处理

结果明确保存：

- `successful_channels`：真正执行成功的渠道，包括成功返回空榜。
- `degraded_channels`：发生运行故障、没有参与融合的渠道。

规则是：

```text
向量成功 + 词法失败 → 使用向量候选，记录 lexical 降级
向量失败 + 词法成功 → 使用词法候选，记录 vector 降级
向量成功为空 + 词法成功为空 → 正常空结果
向量失败 + 词法失败 → HybridRetrievalError
```

两路都失败不能伪装成“知识库没有答案”，否则外部服务宕机时系统会产生错误拒答。

## 为什么当前按顺序执行，而不是 asyncio.gather

两个默认 Adapter 可以使用同一个请求级 `AsyncSession`。SQLAlchemy 的一个 `AsyncSession` 不能被多个协程并发执行 SQL，因此第一版按顺序调用两路。

以后如果性能评测证明有必要并行，需要让两个渠道使用独立 Session，并明确各自事务和连接回收规则。不能只把代码换成 `asyncio.gather()` 就认为安全。

当前延迟主要来自远程 Embedding，`pg_trgm` 约 10 ms，并行带来的收益很小。

## 同一 Chunk 为什么要核对来源

两路使用 Chunk ID 去重。如果相同 ID 却出现不同的：

- 知识库或文档 ID。
- 文件名或 Chunk 序号。
- 正文、标题或页码。

系统会抛出 `HybridRetrievalError`，而不是随便选择一路。否则最终引用可能展示 A 渠道的文件名，却使用 B 渠道的正文，无法审计。

## 真实困难集结果

评测使用同一份 35 题困难集、真实 `text-embedding-v4`、`pg_trgm` 阈值 0.1、每路 12 条候选和 RRF Top-3。

| 指标 | 真实向量旧基线 | Hybrid RRF 候选阶段 |
| --- | ---: | ---: |
| Recall@3 | 76.67% | 76.67% |
| MRR | 79.33% | 73.33% |
| 困难拒答准确率 | 10.00% | 0.00% |
| 平均延迟 | 2770.31 ms | 3041.27 ms |

这里的拒答准确率不能当作最终产品结果，因为 Hybrid 本轮只召回候选，没有执行 EvidenceSelector。但它仍说明：只要取消答案充分性判断，相关候选几乎总能被找到，系统也就几乎不会拒答。

逐题比较发现：

- 没有新增标准证据命中，Recall 保持不变。
- 三个问题的首条正确证据从第 1 名降到第 2 名。
- 一道原本正确拒答的问题因为候选阶段不设向量阈值而产生结果。
- 词面相似的干扰片段获得了额外名次贡献。

## 为什么“没有提升”也要保留记录

评测的目的不是证明每次改动都更好，而是阻止未经验证的技术直接上线。

当前决策是：

```text
保留 HybridRetriever、渠道状态和降级机制
→ 不接入聊天
→ 下一步实现真正的 EvidenceSelector
→ 再用相同困难集评测
→ 指标有净提升才启用
```

如果删除这次负结果，未来很可能再次重复“加关键词检索一定更好”的假设。版本化基线可以解释为什么项目没有盲目使用热门技术。

## 为什么暂时不换 BM25

BM25 比 `pg_trgm` 更适合词项频率和文档长度相关的关键词排名，但本轮主要问题不是词法召回数量不够，而是：

- 词面噪声进入最终排名。
- 系统无法判断候选是否真的包含答案。
- 多证据问题需要第二阶段理解和重排。

现在再加入 BM25 只会增加第三份候选榜，不能自动解决答案充分性。因此 BM25 继续保留为后续对照实验，而不是当前主线。

## 测试保护什么

- 请求清理、知识库去重和双预算边界。
- 两路共同命中时正确累加 RRF 贡献。
- 原始向量、词法和融合分数不会混淆。
- 单路失败显式降级，双路失败明确报错。
- 成功空榜不会被误判为系统故障。
- 权限范围错误不允许降级。
- 同一 Chunk 的来源冲突会被拒绝。
- 真实向量 Adapter 复用已有 SearchService 并恢复知识库顺序。
- 困难集固定记录 Hybrid 没有超过真实向量基线。

## 面试时可以怎么讲

> 我把真实向量和 pg_trgm 接到一个可降级的 HybridRetriever 中，用 RRF 避免直接相加不可比较的分数，并保留每个渠道的名次贡献。权限错误不会被降级吞掉，两路都失败也不会伪装成无答案。真实 35 题评测显示等权 RRF 的 Recall 与向量持平，但 MRR 下降，所以我没有把它直接接入聊天，而是保留内部实验能力，下一步优先解决答案充分性判断。这体现了我用评测决定架构启用，而不是为了技术栈数量盲目上线。

## 15–30 分钟小练习

请用自己的话解释下面三个问题：

1. 为什么 `fused_score=0.03` 不能直接与向量阈值 `0.45` 比较？
2. 为什么“渠道成功但返回空列表”和“渠道抛出异常”不能都记录为空列表？
3. 为什么本轮 Hybrid 代码可以保留，但不能接入聊天？

答案要点：分数来自不同公式；一个是正常业务事实、另一个是系统没有完成工作；真实评测没有产生净提升，并且尚缺答案充分性判断。
