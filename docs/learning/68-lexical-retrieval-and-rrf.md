# 68. 词法检索接口与 RRF 排名融合

## 这一模块解决什么问题

向量检索和关键词检索擅长的场景不同：

- 向量检索擅长同义改写和语义相近表达。
- 关键词检索擅长项目代号、人名、日期、型号和专业缩写。

下一阶段要同时使用两路候选，但两种原始分数不能直接相加：

```text
向量相似度：通常在 -1 到 1 之间
pg_trgm 相似度：通常在 0 到 1 之间
BM25 分数：没有统一上限，并受语料统计影响
```

因此本模块先定义统一词法检索接口，再使用 RRF 根据名次融合，不比较原始分数。

## 在整体架构中的位置

```text
用户问题
├─ Vector Retriever → 向量候选榜
└─ BaseLexicalRetriever → 关键词候选榜
                ↓
       ReciprocalRankFusion
                ↓
         EvidenceSelector
                ↓
       有证据回答或明确拒答
```

本模块只完成内部契约和纯算法。数据库关键词 SQL 会在下一模块实现，因此当前线上检索仍然只走向量渠道。

## BaseLexicalRetriever 负责什么

`BaseLexicalRetriever` 统一下面这些未来实现：

- PostgreSQL `pg_trgm`。
- PostgreSQL BM25 扩展。
- Elasticsearch / OpenSearch BM25。
- 测试使用的 Mock Retriever。

它只定义一个异步方法：

```python
async def retrieve(request) -> LexicalRetrievalResult:
    ...
```

真实数据库或搜索服务都属于 I/O，因此接口从一开始就是异步的。

## 为什么 Request 必须带用户范围

`LexicalRetrievalRequest` 包含：

- `user_id`。
- `knowledge_base_ids`。
- `query`。
- `candidate_limit`。

关键词检索不能先搜索全部 Chunk，再在 Python 中过滤用户。正确顺序必须是：

```text
SQL 中限制当前用户和知识库
→ 限制 READY 文档
→ 计算关键词排名
→ LIMIT 候选数量
```

这与向量 Repository 的权限边界相同。接口提前携带范围，是为了让未来 Adapter 没有借口设计成全库搜索。

知识库 ID 会按首次出现顺序去重，空知识库列表、空问题和无边界候选数量都会在进入数据库前被拒绝。

## LexicalRetrievalCandidate 保存什么

候选包含完整的可追溯来源：

- 知识库与知识库名称。
- Chunk、文档和文件名。
- Chunk 顺序、正文哈希和标题路径。
- 页码、Token 数与正文。
- `lexical_score`。

词法分数约定为“越大越相关”。如果某个数据库运算符返回负距离，Adapter 必须先转换成这一统一方向。

结果还必须满足：

- Chunk ID 不重复。
- 按 `lexical_score` 降序排列。
- 数量不超过候选预算。
- 所有候选属于本次请求的知识库范围。

## 为什么 RRF 不使用原始分数

假设有两个榜单：

```text
向量榜：A、B、C
词法榜：B、D、A
```

RRF 对每个名次计算：

```text
贡献 = 1 / (k + rank)
```

默认 `k = 60`，名次从 1 开始。

那么：

```text
A = 1/(60+1) + 1/(60+3)
B = 1/(60+2) + 1/(60+1)
C = 1/(60+3)
D = 1/(60+2)
```

B 同时在两路靠前，因此最终超过 A。D 比 C 更靠前，是因为两者都只出现一次，但 D 的渠道内名次更高。

## rank_constant 如何理解

`rank_constant` 是平滑常数：

- 常数较小：第 1 名和第 2 名差距更明显。
- 常数较大：相邻名次贡献更接近，更重视多渠道共同出现。

第一版使用常见默认值 60，但它仍然属于需要通过评测校准的参数，不是永远正确的常数。

## 稳定排序

不同 Chunk 可能得到完全相同的融合分数。为了保证测试和线上结果可重复，代码使用“第一次在输入榜单中出现的顺序”处理同分：

```text
先遍历向量榜，再遍历词法榜
→ 同分时先出现的候选排在前面
```

稳定排序很重要，否则数据库或 Python 版本变化可能让引用顺序随机变化。

## 为什么同一渠道不能出现两次

下面的输入是错误的：

```text
vector 榜单 1
vector 榜单 2
lexical 榜单
```

如果允许重复渠道，向量检索会获得两倍投票权。`ReciprocalRankFusion` 因此拒绝重复 `RetrievalChannel`。

同一个 Chunk 在单一榜单中也不能重复，否则它会在同一渠道获得多次贡献。

## MockLexicalRetriever 的作用

Mock 实现可以：

- 返回固定的有序关键词候选。
- 根据候选预算截取结果。
- 记录收到的请求。
- 模拟 BM25 或数据库超时。

它不会访问 PostgreSQL，也不会使用 API Key。下一模块接入真实关键词 SQL 后，Service 集成测试仍可使用 Mock 稳定覆盖失败和边界分支。

## 为什么现在没有数据库迁移

本模块的目标是先确定接口和融合公式。现在创建索引会混入几个尚未验证的决定：

- 使用 `pg_trgm`、PostgreSQL 全文检索还是 BM25 扩展。
- 使用 GIN 还是 GiST 索引。
- 中文采用字符切分还是词语切分。
- 关键词候选数量是多少。

先完成纯算法后，下一模块只需要关注 PostgreSQL 实现和查询计划，出现错误时更容易定位。

## 数据库事务在哪里

这一模块没有数据库操作，因此也没有事务。

未来词法 Repository 只执行读取 SQL，不会主动提交事务。文档 Chunk 仍由入库 Worker 的原子事务创建和替换，检索器只读取处于 READY 状态的 Chunk。

## 失败如何处理

需要区分：

```text
词法榜为空
→ 正常结果
→ 仍可使用向量候选

词法后端超时或返回越权 Chunk
→ LexicalRetrievalError
→ 不能静默当成空榜
```

是否允许“关键词渠道故障时只用向量渠道降级”会在 Service 集成模块中明确设计，并通过日志和指标暴露，不能由 Retriever 自己偷偷决定。

## 替代方案

### 直接相加归一化分数

需要长期维护不同模型与检索器的分数标定。更换 Embedding 或 BM25 语料后，归一化关系可能失效。

### 只取两路交集

精度可能提高，但同义改写只被向量召回、精确编号只被关键词召回时都会丢失，Recall 风险很高。

### 训练学习排序模型

能够学习复杂权重，但需要大量带点击或相关性标签的数据。当前 35 题不足以支撑训练。

RRF 不需要训练、对分数尺度不敏感，很适合当前第一版混合检索。

## 测试保护什么

- Request 清理问题、去重知识库并限制预算。
- Result 禁止越权、超预算、重复 Chunk 和错误排序。
- Mock 返回有界结果并模拟失败。
- RRF 正确累加两路名次贡献。
- 同分时结果稳定。
- 同一渠道和同一榜单的重复项被拒绝。

## 面试表达

> 向量相似度、trigram 和 BM25 分数不可直接比较，所以我没有做线性相加，而是定义带用户范围的 LexicalRetriever，并用 RRF 根据渠道内名次融合。RRF 结果保留每个渠道的名次贡献，便于审计。词法结果还必须通过知识库范围、候选预算、唯一性和排序校验，防止新的检索后端绕过原有权限边界。

## 小练习

预计 15–20 分钟：

已知：

```text
向量榜：A、B
词法榜：C、B
k = 60
```

请计算 A、B、C 的 RRF 分数并写出最终顺序。

答案要点：

```text
A = 1/61
B = 1/62 + 1/62
C = 1/61
```

B 排第一；A 与 C 同分，按照首次出现顺序，A 排在 C 前面。
