# Vue 文档管理界面

## 1. 本模块完成了什么

上一模块已经有文档 API 和 Pinia Store，但用户还不能在页面中操作它们。

本模块把文档能力接入知识库页面：

```text
知识库卡片
→ 展开文档管理区域
→ 选择 PDF / TXT / Markdown
→ 上传文件
→ 查看异步入库状态
→ 失败后重新入库
→ 二次确认后删除
```

现在页面能够展示完整的文档生命周期：

```text
等待处理 → 正在入库 → 可以检索
                    └→ 处理失败 → 重新入库
```

## 2. 为什么采用卡片内展开

可以选择三种常见页面结构：

### 方案一：单独的文档详情路由

优点：空间大，适合复杂筛选和文档预览。

缺点：第一版操作不多，用户需要在知识库列表和详情页之间频繁跳转。

### 方案二：弹窗管理文档

优点：不离开当前页面。

缺点：文件列表较长时弹窗滚动体验差，删除确认框还会形成弹窗套弹窗。

### 方案三：知识库卡片内展开

优点：知识库和它的文档关系直观，适合第一版轻量界面。

缺点：文档很多时卡片会变长。

当前选择方案三，并限制同一时间只展开一个知识库。以后加入分页、文档预览和批量操作时，可以再升级为独立路由。

## 3. 组件为什么要拆分

原来的 `KnowledgeBasesView.vue` 已经负责：

- 创建知识库。
- 加载活动和归档列表。
- 编辑名称和描述。
- 归档和恢复。
- 退出登录。

如果再把文件选择、状态列表、重试和删除全部写进去，页面会同时理解两套业务对象，代码很难沿调用链阅读。

因此新增：

```text
KnowledgeBasesView
├─ 管理知识库生命周期
├─ 决定当前展开哪个知识库
└─ KnowledgeBaseDocumentsPanel
   ├─ 文件选择与校验
   ├─ 文档状态展示
   ├─ 重试操作
   └─ 删除确认
```

这不是新增后端抽象层，而是按可见 UI 区域拆分组件。文档面板仍然直接调用 Document Store。

## 4. 真实调用链

### 4.1 展开文档面板

```text
用户点击“管理文档”
→ KnowledgeBasesView 设置 expandedKnowledgeBaseId
→ 创建 KnowledgeBaseDocumentsPanel
→ 面板调用 documentStore.loadDocuments
→ Store 调用 listDocuments API
→ GET /api/v1/knowledge-bases/{id}/documents
→ Store 按知识库保存返回列表
→ 面板响应式重新渲染
```

### 4.2 上传文件

```text
input change
→ 前端检查扩展名、空文件和大小
→ 保存 File 引用
→ 用户点击“上传并开始入库”
→ documentStore.uploadDocument
→ Document API 构造 FormData
→ FastAPI 接收原文件并返回 202
→ Store 插入 pending 文档
→ Store 开始轮询
→ 页面显示“等待处理”
```

### 4.3 重试失败文档

```text
用户点击“重新入库”
→ documentStore.retryDocument
→ POST /api/v1/documents/{id}/retry
→ 后端创建新的持久化任务
→ 返回 pending 文档
→ Store 替换旧 failed 状态并重新轮询
→ 页面显示“等待处理”
```

### 4.4 删除文档

```text
用户点击“删除”
→ 只打开确认框
→ 用户再次确认
→ documentStore.deleteDocument
→ DELETE /api/v1/documents/{id}
→ 后端执行可恢复两阶段删除
→ 成功：关闭确认框并移除文档
→ 失败：保留确认框、文档 ID 和错误
```

## 5. 文件选择为什么只保存 File 引用

浏览器的 `<input type="file">` 提供 `File` 对象。代码没有先使用 `FileReader` 把完整内容读取为字符串或 Base64。

原因：

- 20 MB 文件读入 JavaScript 会额外占用内存。
- Base64 通常还会让体积增加。
- 上传 API 本来就可以直接把 File 放进 FormData。
- 页面此时不需要预览文件正文。

因此数据流是：

```text
操作系统文件
→ 浏览器 File 引用
→ FormData
→ HTTP 请求体
```

## 6. 前端校验为什么不是安全边界

页面检查：

- 扩展名是 `.pdf`、`.txt`、`.md` 或 `.markdown`。
- 文件不为空。
- 单文件不超过 20 MB。

它的目的只是让正常用户更快看到错误，而不是保护后端。

调用者可以：

- 绕过 Vue 页面直接请求接口。
- 修改文件扩展名。
- 伪造 MIME。
- 修改前端 JavaScript。

所以后端仍必须重新检查：

- 上传大小。
- 允许类型。
- 文件签名和实际解析结果。
- 用户是否拥有知识库。
- 同库 SHA-256 是否重复。

前端校验改善体验，后端校验才是可信业务规则。

## 7. 为什么不能只依赖 MIME

浏览器给 `File.type` 的值可能为空，也可能来自操作系统文件关联，并不稳定。

当前页面先根据文件名扩展名给出即时提示，后端再根据 MIME、扩展名和真实解析结果执行最终判断。

第一版支持：

```text
.pdf
.txt
.md
.markdown
```

## 8. 状态如何展示

页面把稳定协议值转换成中文：

| 协议值 | 页面文字 | 含义 |
| --- | --- | --- |
| `pending` | 等待处理 | 任务已经持久化，等待 Worker |
| `processing` | 正在入库 | Worker 正在解析、分块或向量化 |
| `ready` | 可以检索 | Chunk 与向量已经完成 |
| `failed` | 处理失败 | 本轮任务失败，需要查看错误或重试 |
| `deleted` | 删除清理中 | 后端墓碑状态，正常列表通常不返回 |

状态徽标使用不同颜色，但不能只靠颜色表达。中文文字始终存在，因此色觉障碍用户和自动化测试都能理解状态。

## 9. 哪些按钮在什么状态出现

### pending / processing

不显示删除按钮。

后台 Worker 正在使用文档，第一版没有取消协议。如果允许直接删除，会出现迟到 Worker 覆盖删除状态的问题。

### ready

显示删除按钮，不显示重试。

### failed

活动知识库显示重新入库和删除。

### 归档知识库

可以查看已有文档，但不能上传和重试。删除仍由后端执行最终业务判断。

前端隐藏或禁用按钮只是交互约束，后端权限和状态检查仍然必须存在。

## 10. 为什么切换知识库要卸载旧面板

父页面只保存：

```ts
expandedKnowledgeBaseId: string | null
```

当用户从知识库 A 切换到 B：

```text
A 面板 v-if 变为 false
→ A 组件卸载
→ onUnmounted 调用 stopPolling(A)
→ B 面板创建
→ loadDocuments(B)
```

这样不会在后台继续轮询用户已经看不到的知识库。

离开整个知识库页面时，同一个 `onUnmounted` 也会释放当前面板的轮询。

## 11. 为什么删除必须二次确认

文档删除会清理：

- MinIO 原文件。
- PostgreSQL 文档和任务记录。
- Document Chunk。
- pgvector 向量。

这不是普通的隐藏或归档，因此确认框明确说明不可撤销。

历史消息的引用快照仍然保留，避免旧回答无法审计；但它不等于保留原文件和实时 Chunk。

## 12. 删除失败为什么保持确认框

删除请求可能在下面任一阶段失败：

```text
数据库墓碑成功
→ MinIO 删除失败
→ 数据库物理清理尚未执行
```

如果前端立即关闭确认框并移除文档，用户会误以为已经成功，也找不到再次清理的入口。

失败时页面保留：

- 原文档卡片。
- 文档 ID。
- 删除恢复标记。
- 后端中文错误。
- “继续删除”操作。

只有 Store 确认 204 或恢复态的幂等成功后才关闭确认框。

## 13. 正常、失败和网络异常

### 正常上传

上传按钮在请求期间禁用并显示“正在上传”。收到 202 后清空文件输入，文档立即以 pending 展示。

### 上传被拒绝

保留用户选择或明确清空无效输入，展示后端错误，已有文档列表不消失。

### 轮询失败

仍展示最后一次成功状态，Store 下一周期继续尝试。

### 重试失败

文档保持 failed，不伪造 pending 状态，错误显示在对应文档附近。

### 删除失败

文档和确认框都保留，用户可以再次执行同一清理。

## 14. 无障碍设计

本模块加入了以下语义：

- 文档面板使用带标题的 `section`。
- 展开按钮使用 `aria-expanded` 和 `aria-controls`。
- 业务错误使用 `role="alert"`。
- 轮询提示使用 `role="status"`。
- 删除确认使用 `role="dialog"` 和 `aria-modal`。
- 状态同时使用文字和颜色。
- 文件输入有真实 label。

这些属性同时帮助键盘用户、屏幕阅读器和组件测试定位元素。

## 17. 常见错误

### 错误一：在页面组件里直接 fetch

会绕过统一 Token、错误解析和 Store 状态管理。

### 错误二：把 202 显示为入库完成

202 只表示文件和任务已接收，必须等待 ready。

### 错误三：只检查浏览器 MIME

MIME 可能为空或伪造，最终校验必须在后端。

### 错误四：页面离开后继续轮询

会浪费请求，并可能在切换账号后读取旧状态。

### 错误五：删除失败后关闭确认框

用户会丢失继续执行可恢复清理的入口。

### 错误六：只用红、黄、绿表示状态

颜色不能独立表达业务语义，必须保留文字。

## 18. 面试时可以怎么讲

> 文档上传是异步入库流程，所以我把 HTTP 和状态管理分开：API Client 负责 multipart 协议，Pinia Store 负责轮询和一致性，文档面板只负责交互展示。面板创建时加载文档，卸载时停止对应轮询，避免隐藏页面继续请求。前端会检查扩展名、空文件和 20 MB 上限，但我明确把它视为体验优化，真正的类型、大小和权限校验仍在后端。删除没有做普通乐观更新，因为它横跨 PostgreSQL 和 MinIO；失败时页面会保留恢复 ID 和确认框，允许继续完成两阶段清理。

## 19. 小练习

练习时间约 15～30 分钟。

请完成其中一个：

1. 为 `processing` 文档增加一条组件测试，确认页面显示“正在入库”，并且不存在删除按钮。
2. 给 `formatFileSize` 增加一个 1.5 MB 的测试用例，并说明为什么显示值要面向用户而不是面向数据库。
3. 用自己的话解释：为什么关闭文档面板要停止轮询，但不能清空 PostgreSQL 中的任务？

答案要点：

- `processing` 是后台活跃状态，当前没有取消协议，不能删除。
- 文件大小格式化只影响展示，数据库仍保留精确字节数。
- 关闭面板只代表用户暂时不观察；后台业务任务必须继续可靠执行。
