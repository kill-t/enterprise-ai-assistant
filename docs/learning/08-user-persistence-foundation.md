# 模块 08：用户持久化基础

## 要解决的问题

当前会话接口仍使用固定 UUID，系统没有可登录的真实用户。认证功能的第一步不是签发 JWT，而是先
定义稳定的用户事实：用户如何存入 PostgreSQL、哪些字段可持久化、唯一性由谁保证、事务由谁提交。

本模块只实现用户 Entity、Repository 和数据库迁移，不处理明文密码，也不开放 HTTP 接口。

## 数据结构

`users` 表包含：

- `id`：用户 UUID 主键。
- `email`：登录标识，最大长度 320，并具有数据库唯一约束。
- `password_hash`：密码哈希，禁止保存明文密码。
- `is_active`：账号是否允许登录。
- `created_at`、`updated_at`：创建和更新时间。

当前没有给 `conversations.user_id` 添加外键。原因是旧代码已经可能写入固定 UUID，如果直接增加
外键，已有数据没有对应用户时迁移会失败。会话所有权模块会先设计数据回填，再增加外键与 ORM
关系。

## 调用边界

```text
Auth Service（下一模块）
→ UserRepository
→ SQLAlchemy AsyncSession
→ PostgreSQL users
```

Repository 只负责：

- 创建实体并执行 `flush/refresh`。
- 按邮箱查询用户。
- 按 UUID 查询用户。

Repository 不负责：

- 处理或校验明文密码。
- 标准化邮箱。
- 判断注册业务规则。
- 调用 `commit()` 提交事务。

这些操作由下一层 Auth Service 编排。让 Service 控制提交，可以把“创建用户”和未来的审计记录等
多个数据库操作放在同一个事务中。

## 为什么数据库仍需要唯一约束

注册接口通常会先查询邮箱是否存在，以返回清晰的中文提示。但两个并发请求可能同时查询到“不存在”，
随后同时插入。只有数据库唯一约束可以在并发条件下最终阻止重复邮箱。因此应用检查用于用户体验，
数据库约束用于数据正确性。

## 测试保护的行为

- 用户表不存在明文 `password` 字段。
- `password_hash` 必填，邮箱有长度和唯一约束。
- Repository 创建用户时执行 `add/flush/refresh`，但不提交事务。
- 邮箱和 UUID 查询入口可供后续注册、登录和当前用户解析使用。

## 面试表达

“我把认证拆成持久化、密码安全和 Token 三个小模块。用户 Repository 不接收明文密码，也不提交
事务；邮箱重复既做应用层友好检查，也依靠数据库唯一约束处理并发竞争。”

## 小练习

思考下面两个问题：

1. 为什么不能只在注册前使用 `get_by_email()` 判断重复，而不创建数据库唯一约束？
2. 为什么 `UserRepository.create()` 不调用 `commit()`？

答案要点：并发注册存在“先查询、后插入”的竞争；数据库约束才是最终一致性边界。事务属于完整业务
动作，未来注册可能同时写用户、审计或默认设置，应由 Service 决定统一提交或回滚。
