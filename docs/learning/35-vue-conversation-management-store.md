# Vue 会话管理状态层

## 1. 本模块解决什么问题

会话列表不只是“读取数据”：用户还需要重命名、归档和删除。若把这些请求逻辑直接写在页面按钮中，页面会同时负责 HTTP、加载状态、失败恢复和列表修改，后续增加弹窗会很难维护。

本模块先在 Pinia Store 建立会话管理规则，下一步页面只需要调用对应动作并按状态渲染。

## 2. 调用链与数据流

```text
会话列表中的管理按钮（下一模块）
→ ConversationStore.renameConversation / archiveConversation / deleteConversation
→ conversations API Client
→ FastAPI PATCH 或 DELETE 接口
→ PostgreSQL 更新或删除会话
→ Store 精确更新内存中的对应列表项
→ Vue 根据响应式状态重新渲染
```

浏览器只传会话 ID 和操作数据，后端从 JWT 取得用户身份并校验所有权。因此前端隐藏按钮不是权限控制，真正的越权拦截在后端。

## 3. 为什么操作成功后才修改列表

重命名、归档和删除都可能因为网络或后端错误失败。当前实现遵循“后端确认后更新本地状态”：

```text
发送请求
→ 等待后端成功响应
→ 替换或移除对应会话
```

失败时不改变原列表，避免出现“页面显示已删除、刷新后又出现”的错误印象。另一种方案是乐观更新：先改页面，失败再回滚。它反馈更快，但需要保存快照、处理并发和回滚，本项目当前不需要这层复杂度。

## 4. 三类局部状态

Store 为每一个会话 ID 维护独立状态：

```ts
updatingConversationIds // 正在重命名或归档
deletingConversationIds // 正在删除
actionErrorMessages     // 某个会话最近一次管理操作的错误
```

例如会话 A 在删除时，不会让会话 B 的按钮也全部禁用。`isManagingConversation(id)` 将两类处理中状态合并，页面可用它禁用同一会话的其他管理按钮，防止重复提交。

## 5. 归档后为什么有两种列表行为

默认列表只展示未归档会话：

```text
归档成功 → 从当前列表移除
```

当页面主动请求“包含归档会话”时，归档对象仍在该列表范围内：

```text
归档成功 → 保留该项，但更新 is_archived 为 true
```

这是 Store 的数据规则，而不是页面通过临时 `filter` 猜测出来的规则。

## 6. 错误如何区分

`errorMessage` 仍只处理“加载列表、创建会话”等全局操作。会话管理失败写进：

```text
actionErrorMessages[conversationId]
```

这样下一模块的重命名弹窗或删除确认框能显示正确会话的错误，也不会覆盖整个列表的加载提示。

本模块还在 Store 内做了标题 `trim()` 与空标题校验，避免仅有空格的标题发送到后端；后端仍必须保留自己的校验。

## 7. 测试保护什么

`frontend/src/stores/conversations.test.ts` 覆盖：

- 重命名请求进行中时，该会话被标记为处理中；成功后仅替换这一项。
- 默认未归档列表中，归档成功后该项被移除。
- 删除成功后仅移除目标会话。
- 管理请求失败时原列表不变，错误记录在该会话 ID 下。

这些是 Store 的单元测试：它们 mock API Client，不访问真实 FastAPI 或数据库。协议正确性由 API Client 测试保护，端到端行为再由后续页面测试与后端测试共同保护。

## 8. 本模块没有做什么

- 尚未增加重命名弹窗、归档按钮、删除二次确认和归档筛选页面。
- 尚未提供“取消归档”。
- 删除不提供恢复站；这就是下一步 UI 必须二次确认的原因。
- 没有乐观更新，也没有批量操作。

## 9. 面试表达

> 我把会话的重命名、归档和删除从 Vue 组件下沉到 Pinia Store。Store 按会话 ID 维护局部请求状态和错误，保证一个会话操作中不会误禁用其他会话。对于有副作用的管理操作，我选择后端成功后再更新前端列表；请求失败时保留可靠旧数据，并让错误精确关联到触发操作的会话。

## 10. 小练习

请补充一个 Store 单元测试：当 `includeArchived` 为 `true` 时，归档会话成功后不应从列表移除，而应保留该会话并把 `is_archived` 更新为 `true`。

答案要点：先设置 `store.includeArchived = true`，mock `updateConversation` 返回归档后的对象，调用 `archiveConversation`，最后断言列表仍有该对象且 `is_archived` 为 `true`。
